# Comment-plus: publishing comments and changing item state

The [TUI tutorial](tutorial.md#12-hand-reviewed-work-to-maintainers) covers the controls for comments, closures and reopenings. The composer keeps the target URL visible; its optional Markdown preview renders locally, without contacting GitHub. An external editor pauses the TUI on a private temporary file and returns to the preview. TUI publication needs approval of the exact target, text and any state change. The separate [automated-actions pass](../prompts/automated-actions.md) may publish after an explicit repository and action-type policy, a bounded exact preview, and fresh checks.

A comment on an issue or PR is a conversation comment, not an inline review. An explained closure publishes the comment first, then closes the item; the script checks for text but cannot judge the explanation. A merged PR cannot be reopened. Bulk reopening uses one shared comment but a separate exact plan and outcome for each target; it stops on the first uncertain outcome. After publication, the TUI refreshes the discussion and ledger, and the displayed state updates after the direct GitHub item read is synced.

`EDITOR` may include arguments, such as `nvim` or `code --wait`; the command must wait until editing is finished. If unset, it defaults to `vi`. Imported CRLF newlines become LF and tabs expand to four spaces. Successful imports remove the temporary file; an editor or import failure keeps the current TUI draft and reports the temporary file's path for recovery.

From an install, save the proposed text in a UTF-8 file and preview it:

```sh
bin/comment-plus --expected-repo OWNER/REPO --kind issue --number 123 --body-file /tmp/comment.md
```

The default is an offline dry-run: it prints the target, exact body, `state_change: "none"`, a request ID and an approval hash without saving a proposal or contacting GitHub. `--dry-run` is also accepted. For GitHub Enterprise, include `--host HOSTNAME` in both invocations; the default is `github.com`, independent of `GH_HOST`.

After a human approves that exact plan, repeat the command with the printed values:

```sh
bin/comment-plus --expected-repo OWNER/REPO --kind issue --number 123 --body-file /tmp/comment.md \
  --publish --request-id REQUEST_ID --approve APPROVAL_HASH
```

Use `--kind pr` for a PR. `--body TEXT` is an alternative to `--body-file`. Changing the host, repository, kind, number, body or request ID invalidates the approval hash. The hash binds the plan; it does not authenticate a human or replace their approval. An agent must obtain the human's explicit approval of the target and text before publishing.

For an action prepared from a selected live observation, add `--expected-updated-at TIMESTAMP` to both commands for an issue or PR, and `--expected-head SHA` for a PR. The exact plan binds those revisions. Publication rechecks them before recording or sending a write, regardless of whether the operation is a comment, closure or reopening. A changed revision requires a fresh proposal and review.

For a closure, add `--close` to both commands. The dry-run plan then shows `operation: "close"` and `state_change: "closed"`. Approval covers the comment and state change together. Publication checks that the live item is still open, posts the comment, and sends a `PATCH` with `state: "closed"` to the issues endpoint for an issue or the pulls endpoint for a PR. A changed or already closed target stops before the comment. A failed close after a successful comment leaves the comment published and records the close outcome as unknown.

For reopening, add `--reopen` to both commands instead. The plan shows `operation: "reopen"` and `state_change: "open"`. Publication checks that the live item is closed and, for a PR, that it is not merged before posting. It then comments and sends a `PATCH` with `state: "open"`. A failed reopen after a successful comment leaves the comment published and the state outcome unknown. For a TUI bulk reopening, each item has its own request ID and saved outcome; successful earlier items are not repeated after a later failure.

Publishing verifies the live target, then records the attempt in `data/<owner>/<repo>/writes/<request-id>.json` before sending the comment. Comment and state-change outcomes are separate; comment-only requests record `not_requested` for the state change. These records are local replay-protection and recovery state, owned by `bin/comment-plus` and Git-ignored even in adopted installs. The request ID and approval hash prevent a repeated request from posting again; the attempted text, target and outcome let you inspect an interrupted request. They are separate from evidence and ledger review status. Deleting a record removes replay protection for its request ID. Publishing never marks a decision reviewed or changes cached evidence.

Repeating a successful request returns its saved result without another write. An interrupted request or failed POST or PATCH has an `unknown` outcome: GitHub might already have accepted it. The same request is never automatically retried. Inspect GitHub and the saved record before preparing and approving a new request; a new request ID can post the same text again. Replay protection applies within this install; it is not a GitHub idempotency guarantee.

An `action-proposals` item can enter another action cycle after a completed write, such as closing and later reopening the same issue. Read the new live state and saved outcome, update the local action guidance, and prepare a new exact proposal with `--replace-checkpoint` set to the completed proposal's checkpoint. The script verifies the completed write receipt, keeps the earlier action in history and gives the new proposal its own request ID and approval. Pending proposals with a write attempt and uncertain outcomes cannot be replaced this way; inspect and reconcile them first. Questions and reconsideration from the completed cycle do not approve the new action.

The implementation uses GitHub's [conversation comment endpoint](https://docs.github.com/en/rest/issues/comments#create-an-issue-comment), shared by issues and PRs, and the [issue](https://docs.github.com/en/rest/issues/issues#update-an-issue) or [PR](https://docs.github.com/en/rest/pulls/pulls#update-a-pull-request) update endpoint for state changes. Automated tests use fake `gh` in disposable installs.

`bin/install-to` maintains the ignore rule. Rerun the installer to apply it to an existing install. Ignore rules do not untrack records already added to Git or remove them from past commits.

## Saved action proposals

The [PR closure playbook](../prompts/recommend-auto-close.md) saves an exact explanatory comment through `bin/action-proposals propose`, the same record used for comments, issue closures and reopenings. Proposal records in `data/<owner>/<repo>/action-proposals/` are Git-tracked; local viewed and dismissed flags are ignored. Saving or viewing a proposal never writes to GitHub or marks a ledger decision reviewed. A PR closure recommendation may omit a saved ledger action, in which case it always requires human approval.

For a named PR or [selected group members](groups.md#from-draft-to-maintainers), the review loop is:

1. The agent reads current local guidance, earlier objections and selected evidence. It reports a justified keep-open outcome or saves an explained closure proposal.
2. In **Notifications**, the reviewer checks the target, exact comment, human guidance and gaps. `e` edits a pending proposal; `d` rejects it with an optional reason and dismisses its notification. On other notifications, `d` only dismisses local presentation. Canceling a rejection records neither action.
3. If guidance changed, prepare a replacement from current context and review it again. If a GitHub write was attempted, inspect its saved outcome before another action. In the staged path, the reviewer approves the exact final comment and close action with `a`; neither group readiness nor ledger review supplies that approval. An action-bound PR closure can use direct execution only when Settings enables its type and the bounded action pass verifies complete selected evidence with no unresolved gap or earlier rejection.

A closure proposal carrying `--decision-question` stays staged under every Settings mode. In Notifications, `r` records an attributed answer to that question without changing the ledger or publishing the answer. The next exact review shows the question and answer beside the PR target and proposed public comment. Its approval binds that version; changing the answer or comment invalidates the earlier approval. Human approval may then use the same `comment-plus` closure writer, while `action-proposals execute --automation` continues to refuse the questioned proposal. Older proposal histories with a resolution recorded after a ledger review remain readable.

`bin/action-proposals --expected-repo OWNER/REPO inspect --kind pr --host HOSTNAME --number N` performs two read-only REST GETs. It returns the PR head SHA and the issue endpoint's `updated_at`, which `bin/comment-plus` checks again before publishing a proposed closure. The read does not create a proposal or grant approval.

An exact `--replace-checkpoint` can update a pending proposal before any write attempt. The previous version remains in the tracked record and the updated proposal appears as new attention, even if the old version was dismissed. A rejected proposal can be reconsidered through the same option with an attributed explanation, as described below. An uncertain write must be reconciled before another action; a completed action can begin a new cycle with fresh guidance and evidence.

For a text-only human edit, `bin/action-proposals --expected-repo OWNER/REPO edit --kind pr --number N --checkpoint CHECKPOINT --comment-file /path/to/comment.md --by NAME` reuses that checkpoint-checked replacement. It preserves the selected context, group handoff and evidence references, revalidates them and retains the previous proposal in history. Notifications offers the same operation with `e` on a pending proposal: edit the exact comment, use `Ctrl-E` for `$EDITOR`, and press `Ctrl-S` to save. A failed save keeps the draft. The edited version gets a new checkpoint and request ID, so the earlier approval or selected-set plan cannot publish it; review the new version before approval. A prior write attempt prevents editing.

New proposals declare the current `item-context` checkpoint and any selected fixed cache snapshots. A group handoff also declares every exported member checkpoint. `propose` checks these offline inputs before saving and includes their revisions, selected component references and explicit evidence gaps in the proposal checkpoint and exact review. Evidence checks establish provenance and coverage, not approval or correctness.

`action-proposals review` rechecks the current ledger/group guidance, prior feedback and selected immutable evidence against the saved proposal. For a group handoff it also checks the group's revision, membership and every exported member checkpoint. An edit to relevant guidance, membership or rejection, or unavailable selected evidence, stops exact review until a new proposal is prepared from current context or the evidence is restored. `execute --publish` checks each pending proposal and its selected evidence again immediately before starting a new `comment-plus` request; a change stops that proposal and the rest of the selected set before another GitHub write. Successful write outcomes produced earlier in that same approved batch do not invalidate its remaining group member checkpoints; other feedback and guidance changes still do. A request with an existing write receipt is reconciled against that receipt first, even if local guidance or evidence changed after the attempt. The local check and GitHub publication have no shared transaction: an edit after the final check can race the write. `comment-plus` independently checks the live target, PR head and activity before posting.

`bin/action-proposals --expected-repo OWNER/REPO context --kind pr --number N --checkpoint CHECKPOINT` checks one saved proposal against current local guidance without GitHub or managed-data writes. It returns a bounded `item-context` page, the latest attributed objection and a `current` flag with a reason when review is unavailable. Use `--offset` and `--context-checkpoint` with the returned item-context checkpoint to read another page. Notifications uses this reader when opening a proposal and again while preparing exact review, so changed group handoffs and local decisions are marked before approval.

To reject one pending proposal with shared feedback, use its exact checkpoint from `bin/action-proposals --expected-repo OWNER/REPO list`:

```sh
bin/action-proposals --expected-repo OWNER/REPO reject --kind pr --number N --checkpoint CHECKPOINT --by NAME --reason 'Why this proposal should not proceed'
```

The reason is optional; omit `--reason` to save an empty one. The tracked proposal keeps the earlier version and records who rejected it, when and any reason provided. Rejection refuses stale checkpoints and any saved GitHub write attempt; it makes that version ineligible for review or execution without changing the ledger or GitHub. In Notifications, pressing `d` on a pending proposal opens the Comments floating window for an optional reason; `D` opens that reason directly in `$EDITOR`. Once the composer is open, `Ctrl-E` opens its current draft in `$EDITOR` from editing or preview. Both entry points return to the same proposal preview, where `Ctrl-S` rejects the exact proposal and dismisses the combined notification. One `Esc` cancels the floating window before submission, including from preview. On a notification without a pending proposal, `d` only dismisses it. A rejected proposal remains in shared history and item context but leaves Notifications as a proposal source; any other notification sources for that PR remain available. Dismissal remains separate local presentation state. If rejection succeeds but dismissal fails, the TUI reports the partial result and any remaining sources can be dismissed separately.

To reconsider, read current `item-context` (and export the group again for a group handoff), then use `propose` with the rejected proposal's exact checkpoint and `--reconsideration-reason 'What changed or which attributed human resolution permits this proposal'`. Supply the usual current context, selected evidence or explicit gap, and exact comment; `--by` attributes the new proposal and its explanation. A missing reconsideration explanation, stale checkpoint or saved write attempt is refused. The rejected version and its reason remain in history and in the next item or group context. The new proposal's `reconsideration` field names the rejected checkpoint and appears in `list` and exact `review` output. A later edit to that pending proposal retains the explanation and objection. The script checks this history and the required explanation; a reviewer judges whether it actually addresses the objection. Resolve conflicting human guidance through attributed ledger or group guidance before proposing again. Reconsideration creates a new request ID and checkpoint, so an older approval cannot execute it.

`bin/item-context --expected-repo OWNER/REPO read --kind pr --number N` carries prior rejections and recorded execution or uncertainty into the next offline pass. A pending proposal with a saved write receipt appears as an unreconciled attempt. Its `feedback_checkpoint` is separate from the ledger/group context revision. Saving a pending proposal with no earlier feedback leaves that checkpoint absent, so the proposal does not make its own reviewed inputs stale. Recorded success is an action outcome, not confirmation that the recommendation was right.

Notifications shows actionable proposals first. The [tutorial](tutorial.md#11-track-follow-up-activity) covers review controls and the `y` agent handoff. Completed proposals move to Past actions and remain in the shared record; rejected proposals leave Notifications, while uncertain outcomes stay under Needs attention. A failed or uncertain close stops the remaining selected actions. The script's separate `dismiss` command excludes a proposal from the active set while retaining its record; marking it viewed changes presentation only.
