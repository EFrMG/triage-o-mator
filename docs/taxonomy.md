# Taxonomy and triage guidance

Each install owns `config/taxonomy.json`. Its `label_catalog` contains GitHub label definitions observed for the selected repository; `observed_at` records the last successful online read, while `pending` means no catalog has been read for that repository. Optional local `guidance` stays attached to a GitHub label ID across renames. Removed labels move to `retired`, and switching repositories archives the previous catalog. `bin/label-catalog sync` refreshes definitions without writing to GitHub. New decisions propose zero or more names from the observed catalog in `proposed_labels`; the separate `labels` field records GitHub's observed item labels.

Settings → Labels can create or edit one GitHub label after a live preview. Press `i` to take the current GitHub catalog as authoritative and add any missing starter labels: `bug`, `enhancement`, `documentation`, `question`, `duplicate`, `needs-info`, `verified`, and `ready`. Existing definitions remain as they are. On a PR, proposing `ready` means its code was read and nothing blocks merging: the TUI's **Merge-Ready PRs** list, the report's merge-ready section and `bin/next`'s code-review suggestion read that proposed label, alongside the legacy `merge-ready` category on older rows. The script `bin/label-definitions --expected-repo OWNER/REPO --initialize-defaults` provides the same exact preview; applying it requires `--apply --preview-sha256 HASH`.

Press `I` to use the install's saved, observed `config/taxonomy.json` label catalog as authoritative, including its custom labels. Its preview lists exact creations, edits, and deletions needed to make GitHub match that local catalog. Deleting a repository label also removes it from issues and pull requests. The script form is `bin/label-definitions --expected-repo OWNER/REPO --reconcile-local`, with the same preview hash required for `--apply`. A pending catalog cannot be used as the local source. A changed local file or live GitHub catalog invalidates the preview; after a partial write, preview again to resume from the saved local target. Installation and catalog sync never write GitHub label definitions.

`action_guidance` in the JSON describes the active action names. `action_operations` maps each name to `none`, `comment`, `close`, or `reopen`. An action is a suggested conversation or state operation, independent of proposed labels. Use `reason` to say what to ask or explain and why. Selecting or reviewing an action does not publish it. A close or reopen operation publishes an explanatory comment first. Settings → Actions edits local names, guidance, and operations through `bin/taxonomy-settings`.

Two `bin/taxonomy-settings` commands have no Settings screen; both change only `config/taxonomy.json`, never GitHub:

- `bin/taxonomy-settings set-guidance --expected-repo OWNER/REPO --label-id ID --expected-name NAME --expected CURRENT --value TEXT` saves local guidance for one label in the observed catalog. `ID` and `NAME` are the label's values in `label_catalog`, and `CURRENT` is the guidance saved now (`""` when there is none); a renamed label or changed guidance is refused so a stale edit cannot overwrite a newer one. With `--action NAME` in place of the label options it edits an action's guidance.
- `bin/taxonomy-settings simplify-actions --expected-repo OWNER/REPO` previews replacing the older default action titles (`no-action-needed`, `comment-request-info`, `close-duplicate` and the like) with `none`, `comment`, `close` and `reopen`. Custom actions stay in the list, and the older titles keep their `action_operations` entries so saved decisions remain readable. Repeat it with `--apply --preview-sha256 HASH` from that preview to write.

Settings → Automations stores each writing action's `stage` or `execute` mode for the selected repository. Each type begins in `stage`; `none` has no write mode. Editing an action resets its mode to `stage`. A decision question always stages its action. The separate labeling pass reads proposed labels regardless of action or ledger review, and runs only when explicitly started for a repository where Labeling is ON. Neither pass confirms a ledger decision.

`low`, `medium`, and `high` express confidence in the proposed triage call. Use `low` when the evidence is thin or disputed. If no observed label fits, leave `proposed_labels` empty, explain the gap in `reason`, and propose a new label to a maintainer through Settings. For duplicates, name and check the other item. For closure, name the checkable basis. Keep the reason short enough to scan, and put the longer evidence in notes or a report. Only a human marks a decision reviewed.
