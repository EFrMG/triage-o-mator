# Taxonomy and triage guidance

Each install owns `config/taxonomy.json`. Its `label_catalog` contains GitHub label definitions observed for the selected repository; `observed_at` records the last successful online read, while `pending` means no catalog has been read for that repository. Optional local `guidance` stays attached to a GitHub label ID across renames. Removed labels move to `retired`, and switching repositories archives the previous catalog. `bin/label-catalog sync` refreshes definitions without writing to GitHub. New decisions propose zero or more names from the observed catalog in `proposed_labels`; the separate `labels` field records GitHub's observed item labels.

Settings → Labels can create or edit one GitHub label after a live preview. **Initialize defaults** previews and creates only missing starter labels: `bug`, `enhancement`, `documentation`, `question`, `duplicate`, `needs-info`, `verified`, and `ready`. Existing definitions remain as they are. The script `bin/label-definitions --expected-repo OWNER/REPO --initialize-defaults` provides the same exact preview; applying it requires `--apply --preview-sha256 HASH`. Installation and catalog sync never create labels.

`action_guidance` in the JSON describes the active action names. `action_operations` maps each name to `none`, `comment`, `close`, or `reopen`. An action is a suggested conversation or state operation, independent of proposed labels. Use `reason` to say what to ask or explain and why. Selecting or reviewing an action does not publish it. A close or reopen operation publishes an explanatory comment first. Settings → Actions edits local names, guidance, and operations through `bin/taxonomy-settings`.

Settings → Automations stores each writing action's `stage` or `execute` mode for the selected repository. Each type begins in `stage`; `none` has no write mode. Editing an action resets its mode to `stage`. A decision question always stages its action. The separate labeling pass reads proposed labels regardless of action or ledger review, and runs only when explicitly started for a repository where Labeling is ON. Neither pass confirms a ledger decision.

`low`, `medium`, and `high` express confidence in the proposed triage call. Use `low` when the evidence is thin or disputed. If no observed label fits, leave `proposed_labels` empty, explain the gap in `reason`, and propose a new label to a maintainer through Settings. For duplicates, name and check the other item. For closure, name the checkable basis. Keep the reason short enough to scan, and put the longer evidence in notes or a report. Only a human marks a decision reviewed.
