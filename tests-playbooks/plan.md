# Playbook evaluation plan

**This is the current plan for the next run.** Start here. It is written for the evaluator: agents under test never receive this file or any path into this kit. Run records are local and not part of this shared kit: fixture designs, old protocols and results live under `DOCS/triage-playbook-evals/seed/runs/`, verified captures under `DOCS/triage-playbook-evals/archives/`. Paths below that start with `seed/runs/` or `archives/` are inside that records directory. For the latest result, open the **highest-numbered completed run's report** from the local run index, `seed/runs/README.md`. Past outcomes are evidence for this plan, not results to copy into a new run.

## What the evaluation is for

Assess whether triage-o-mator's **playbooks help an agent make and communicate sound decisions** while its scripts preserve evidence and enforce write boundaries. A synthetic PR about some example, tests whether a reviewer spots a contradiction between a PR claim and its diff. It is not a test of lazygit features. Product behavior requires its own build or runtime test and must be reported separately.

Keep four kinds of work distinct:

1. **Judgment cases:** small, pinned issue/PR selections with positive, negative and unresolved examples. Two independent agents see the same immutable evidence and receive an explicit task for each playbook being assessed.
2. **Coverage passes:** bounded batches that test selection, screening, checkpointing and briefing at scale. A 150-item checkpoint does not mean 150 judgments were adjudicated.
3. **Script and UI safety cases:** exact previews, stale evidence, approval and fault injection. A unit test, dry run and live private write are different observations.
4. **Real public cases:** historical frozen lazygit evidence for editorial complexity. It is read only and cannot establish today's backlog state without a separately budgeted live read.

The expected-answer guide describes checkable fixture facts and acceptable uncertainty. It does not prove a synthetic product bug reproduces or that one agent's recommendation is automatically right.

Use private synthetic items for checkable relationships and write safety, and frozen real public items for long-lived discussions, multiple authors, conflicting evidence and editorial judgment. A private fixture written by one account over a short period cannot supply authentic maintainer feedback or age. Keep private and public denominators separate and never present a synthetic report as an upstream lazygit finding.

Use **two lanes**. A natural workflow lane starts with a maintainer-style request, such as triaging the next 25 untriaged issues, reviewing one named PR, or preparing a brief for recently updated items. The agent follows the installed playbook, chooses the bounded selection with the normal scripts, acquires permitted evidence and hands work to a person as it would in real use. A diagnostic lane gives one named playbook a small fixed case set with known positive, negative and unresolved controls. The natural lane tests selection, sequencing and handoffs; the diagnostic lane isolates why a specific judgment succeeds or fails. Keep their denominators and conclusions separate. Do not turn every natural task into a list of seeded targets or tell the agent which contradiction to find. For example, give an agent a frozen install and ask for a 25-issue first pass and one maintainer brief, without naming the hidden control issues. Audit what it selected, what it skipped, how it used evidence and whether the brief helps a person decide. Run an independent copy of the same request if consistency matters.

A realistic request can be: _Triage the next 25 untriaged issues in this pinned repository, propose labels where the catalog fits, mark only concrete maintainer decisions for Pending review, and write one brief. Do not publish comments or change item state._ Let the agent use the normal selection and evidence scripts, choose whether duplicate or scoring work is needed, and leave a handoff another agent or maintainer could continue. A separate realistic PR request can ask for review of a named PR and a keep-open/close/defer recommendation using its diff, base context and discussion. Neither request should force every playbook to run; measure the playbooks the agent actually used and record those it did not use.

## Before a new run

Choose a new short run ID and create a **run-specific fixture file** at `seed/RUN_ID.json` **in the local records** before running the seed. It stays out of this kit until the run is over. `seed/fixtures.json` provides the pinned base topics and repository; the per-run file supplies expanded cases using the schema described in [seed mechanics](seed/README.md). Add an explicit `public_read_scope` (repository, corpus ID, inventory snapshot, source commit and fixed-snapshot offline mode) and `briefing_batches` with positive issue/PR batch sizes that cover the planned counts. Save the withheld answer guide at `seed/runs/RUN_ID/gold.json`. The seed and handoff refuse an unknown run ID or missing scope/guide, so a future run cannot silently inherit an older fixture shape, public corpus, batch plan or answer guide. Review remote-visible titles, bodies, comments, paths and diffs for leaked answer roles. Keep the public source checkout pinned and clean.

After seeding, audit the **initial** private state before agent work: repository identity/privacy, exact item titles and bodies, follow-up comments, one-file PR diffs and heads, Actions/Dependabot state, label catalog, staged action policy, a fresh ledger and absence of old/bot backlog. If any differs from the approved preview, stop. Do not treat the seed audit as a playbook verdict.

Write a case manifest under `seed/runs/RUN_ID/` before any agent pass. It must name the repository, program/playbook hashes, source inventory or corpus, budget, intended playbook and planned positive/negative/unresolved controls. For a **diagnostic** task, freeze exact selected keys, immutable snapshot IDs, source revisions, required components and direct comparison pairs before assignment. For a **natural workflow** task, freeze the starting inventory, selection rule and budget; the agent's selected keys and snapshots are outputs to record and adjudicate afterward. If an acquisition has not yet produced a snapshot, record that as an acquisition task and freeze its resulting ID before asking for a diagnostic judgment. For PR claims about existing behavior or documentation, make the operative diff **and the pinned base file or surrounding code** available. Add discussion, reviews and checks when the recommendation needs them. A missing component stays a gap; do not silently borrow it from a different snapshot.

Before seeing agent outputs, write the case-level acceptance criteria and allowed uncertainty in a withheld guide. Name what would count as an unsupported public comment, false duplicate, false ready or false close call, and what evidence could justify `none`, distinct or defer. Include a few cases drawn from real past failures and rotate held-out cases so the run does not become a test of memorized fixture patterns. Recheck the task wording against the grading rule; an agent should not be penalized for following the stated task.

Give every agent its own installs with `run-eval.sh agent-install RUN_ID AGENT`. It builds `/tmp/triage-eval-RUN_ID/AGENT/` (or under `TRIAGE_EVAL_AGENT_ROOT`) with a `private/` clone carrying a copy of the audited seed install, a `public/` clone of the pinned lazygit checkout carrying the frozen evidence cache and inventory, and a copy of `agent-handoff.md`. Both clones are at their pinned commits, so base files are readable for PR review. The public install's ledger is rebuilt as inventory only: earlier agents' decisions, scores, assessments, batches, briefs and reports are not copied. Its evidence cache is copied whole, so snapshots acquired outside the frozen corpus are still present; diagnostic tasks name exact snapshot IDs for that reason. The command refuses to run if the seeded install, either source checkout or any playbook changed since `test-start`, and records each agent's paths, heads and install digest in `seed/runs/RUN_ID/agent-installs.json`. Start each agent in its own directory and keep the seed's install at `/workspace/lazygit-test` untouched until the blind outputs are sealed; it is the base for later agents and for the serial write phase. **This whole kit is evaluator-only.** `test-start` writes two files: `test-handoff.json`, the evaluator's freeze record, and `agent-handoff.md`, a self-contained description of the starting state with no links or paths into the kit. A blind agent receives a copy of `agent-handoff.md` and its task text, and nothing else from here: not this plan, the run directory, `seed-state.json` (its keys carry case roles), the fixture preview, seed source, audit, expected answers, prior reports or other agents' notes. Each agent's data is separate, but an install's program links still resolve to this checkout, so the kit stays reachable on disk; the boundary is the instruction in the handoff plus the agent's command log, and the report must say so rather than claim enforced isolation. Fix the model and reasoning settings in the manifest. If a selected snapshot or case list changes, create a new version of the case manifest and mark the earlier pass separately.

Hold the fixture and program still during a blind comparison. Finish the initial audit and snapshot selection, then make **no GitHub or source edits affecting selected items, no policy changes and no program/playbook commit changes** until both agent outputs are sealed. Run private write-safety cases afterward on separately identified items or in a new phase with fresh revisions. Recheck repository identity, source HEAD and playbook hashes at the end. If a source or program revision changes, stop the affected comparison and record a new packet; do not quietly combine before/after observations. An earlier run allowed evaluator-side writes during ongoing briefing and saw an unrelated program HEAD change, which made this boundary harder to explain.

Separate fixture preparation from blind adjudication where possible. A preparer may inspect the seed and guide to verify the fixture; the blind evaluator should not read that material until both agents' first outputs are saved. If one person must perform both roles, record the prior exposure and avoid claiming evaluator blindness. The local run index links earlier reports where this distinction mattered.

## Assign agents and bounded playbook tasks

**One task per playbook pass does not mean one subagent per playbook.** In the natural lane, one agent can own a coherent maintainer request across playbooks so that selection, local decisions, handoff and brief are tested together. Save a checkpoint at each playbook boundary. In the diagnostic lane, give a bounded task for one named playbook; the same agent may take another task after its output is sealed if independence is not the measure. Use two fresh, isolated agents on the **same** task and packet when measuring judgment agreement. A single agent per playbook gives no same-case replication and can hide failures between playbooks. Keep live GitHub writes with one serial operator after the read passes.

Two independent attempts reveal disagreements; they do not estimate a reliable accuracy rate. If a future report needs a rate or before/after comparison, repeat the same frozen tasks across additional trials with the model, budget and environment held fixed, and keep the per-trial traces. Do not turn two matching answers into a confidence score.

**The handoff is not a task.** It states the repository, counts, commits and public scope, and tells the agent to wait for task text. Every request in either lane is a separately written task, saved under the run directory before it is sent. The `briefing_batches` sizes recorded in `test-handoff.json` are the evaluator's planned denominator for the Maintainer brief coverage task; put them in that one task's text, not in front of every agent.

Do not ask an agent to apply several playbooks wherever they seem relevant in a **diagnostic** task. Each such task should specify: the named installed playbook; exact keys and snapshot IDs; required evidence categories without revealing the intended finding; the owning script record or brief to save; the request/time bound; allowed side effects; and what to report when the answer is `none`, distinct, deferred or unassessed. For an independent comparison, give both agents **the same packet and task text** in isolated installs, then seal both outputs before either sees an answer guide or the other's notes. Save the actual task text and a command/tool-call log under the run directory; record failures and retries as well as successful outputs.

Use this task form, filled with real paths and IDs:

> Follow `prompts/PLAYBOOK_NAME.md` for these exact `KIND:NUMBER` keys and immutable snapshots. Read the listed body, complete discussion, operative PR diff and pinned base context; inspect the strongest fact against your likely call. Stay within `N` acquisition requests. Save the playbook's owning record or brief for **every** selected key, including no-finding or deferred outcomes. Report selected and remaining keys, revisions, gaps, requests, elapsed time, record IDs and any correction. No GitHub write is authorized by this task.

Do not force a positive result just to fill a matrix cell. If the fixture has no defensible PR close, record zero positive closes and leave that branch untested. A later task to edit a brief, change a head or inject an uncertain response must be separate from the sealed blind comparison. For natural workflow tasks, record the person's original request, what the agent selected, what it left behind and the final artifact a maintainer would actually read; grade the end state and tool path, not only a final sentence.

## Planned case matrix

Select an inspectable denominator for each row and freeze it in the case manifest. These are **requirements for a future run**, not claims about any past run.

| Playbook or flow      | Minimum decision contrast                                                                                              | Required output and main risk                                                                                                                                 |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Prepare analysis      | Complete, partial and interrupted/resumed acquisition.                                                                 | Corpus/job status and fixed snapshots; finished progress must not imply coverage or freshness, and offline reads make zero requests.                          |
| Auto triage           | Useful unanswered question, already-answered or repeated question, and a true `none`/defer.                            | Source-bound decision for every key; count unjustified public comment suggestions separately.                                                                 |
| Label items           | Clear match, no fit, stale catalog and human correction.                                                               | Local proposals/no-fit records plus exact item-label preview and bounded outcomes; preserve unrelated labels.                                                 |
| Score items           | Same pinned issues/PRs scored blind twice, an evidence gap, and distinct content/metadata/head freshness changes.      | Dimension reasons and marks, current/unassessed status and stale refusal; agreement is not correctness.                                                       |
| Find duplicates       | Same cause with different words, same title with different cause, unresolved discriminator and recorded not-duplicate. | Both-sided direct signals and saved verdicts; no safe survivor inferred from title or shared defect alone.                                                    |
| Review PR             | Obvious wrong diff, plausible but redundant or unsupported doc edit, partial diff, and safe no-finding control.        | Head-bound review assessment with operative diff **and base context**, contrary facts, reviews/checks or named gaps.                                          |
| Recommend PR closures | Justified close, keep-open and defer, with changed head/activity control.                                              | Exact explanation and pinned state; an absent positive fixture is explicitly untested.                                                                        |
| Organize groups       | Relevant mixed issue/PR set, no-group control and edited-scope case.                                                   | Frozen candidate origin, member relevance and one clear maintainer question.                                                                                  |
| Automated actions     | Stage, question/answer edit, rejection, stale preview, direct execute and uncertain transport.                         | Exact proposal, policy, preview, receipt and before/after state. Use fake GitHub for fault injection; live private writes are separately approved and serial. |
| Maintainer brief      | Distinct bounded batches, including a PR batch with diffs.                                                             | Screen every selected member, checkpoint only screened batches, and expose important omissions and counterarguments.                                          |
| Polish briefs         | Four saved briefs, a conflict between calls, and an edited source after planning.                                      | One readable master bound to exact input digests; audit what useful nuance disappeared.                                                                       |
| Item brief            | One issue and one PR with a material contrary fact or gap.                                                             | Decision, evidence link, strongest hesitation and next check; no implied write approval.                                                                      |
| Review appeal         | Closed PR with original and competing claim, later discussion and incomplete-source control.                           | Pinned watch/action reads that separate claims, observed closure, appeal and approval; no automatic reopen.                                                   |
| TUI integration       | Public frozen and private fixture navigation through batches, briefs, scores, notifications and Pending review.        | PTY steps, blocked-network proof, preserved drafts/scroll and stale-reply behavior; startup alone is not offline proof.                                       |

## Adjudicate and write one report

Score **selection coverage, evidence fidelity, judgment, handoff clarity and side-effect safety separately** for every tested case. Count selected, completed, skipped, deferred and untested keys. Report false positive comments and closes apart from missed useful work. A completed record proves the scope was handled; it does not validate the recommendation. Compare the two blind answers first, then inspect the withheld guide and full source. Record source corrections, especially a wrong snapshot pin or a missing base document, without rewriting the original blind answer.

Save **one** `seed/runs/RUN_ID/report.md`. It is both the shareable discussion update and the technical result. Open with plain-language answers to: what was tested, what happened, what worked or failed, and what remains unknown. Then include a per-playbook status table (`observed`, `partly observed`, `not tested`) with denominators, a disagreement/correction section, exact side effects and evidence links. Keep full keys, revisions, hashes, request counts, task text, receipts and raw observations in linked run records rather than crowding the opening. Never call seeded, planned, dry-run or unit-test cases live playbook results. Do not make a second `discussion_*.md` or `summary.md` for a new run.

The report must distinguish synthetic private cases from public real cases, a source-based PR finding from runtime reproduction, and a saved local suggestion from a GitHub write. State whether the report was posted anywhere; writing the file alone is not publication. Preserve the previous run's report and ratings as historical evidence, not a denominator for the new run.

Keep local triage decisions, explicit Pending review requests and GitHub write approval as separate states. A group, score or brief can support a human decision without flagging Pending review or authorizing an action. For each live private write, retain the exact target, operation, public text, policy, preview/approval hash, live recheck and receipt; closure or reopening posts its explanation first. No public repository write is permitted.

## Reproducible run and archive sequence

`README.md` is the short entry point; this plan is the single current method. `seed/README.md` explains fixture mechanics. `run-eval.sh` and `archive-run.sh` are the owning run tools. Check the current private remote before planning. An old local clone may remain, so pass the matching verified previous archive when the seed requires it.

```sh
KIT=/workspace/triage-o-mator/tests-playbooks
RECORDS=/workspace/triage-o-mator/DOCS/triage-playbook-evals # local; override with TRIAGE_EVAL_RECORDS
: "${RUN_ID:?Set an unused run ID after reviewing seed/RUN_ID.json}"
archive_args=()
if [[ -n ${PREVIOUS:-} ]]; then
  $KIT/run-eval.sh verify "$PREVIOUS"
  archive_args=("$PREVIOUS")
fi
$KIT/run-eval.sh plan "$RUN_ID" "${archive_args[@]}" # read-only preview; save and review its hash
$KIT/run-eval.sh seed "$RUN_ID" PLAN_SHA256 "${archive_args[@]}" # private GitHub writes only after exact seed approval
$KIT/run-eval.sh test-start "$RUN_ID" # audit before agent work; writes test-handoff.json and agent-handoff.md
$KIT/run-eval.sh agent-install "$RUN_ID" a # one isolated directory per agent under /tmp
$KIT/run-eval.sh agent-install "$RUN_ID" b
# Freeze case manifest and exact agent tasks; run bounded passes; write report.md.
$KIT/run-eval.sh archive "$RUN_ID" ARCHIVE_NAME
$KIT/run-eval.sh verify "$RECORDS/archives/ARCHIVE_NAME.tar.gz"
# After separate approval of the exact repository deletion:
$KIT/run-eval.sh delete "$RECORDS/archives/ARCHIVE_NAME.tar.gz" --confirm-repo OWNER/REPO
```

Set `PREVIOUS` to the matching verified archive when an old local clone exists; leave it unset only for a genuinely fresh target with no old clone or remote. If the previous remote still exists, `plan-after-reset RUN_ID PREVIOUS_ARCHIVE` makes a read-only prospective preview only after verifying it still matches the archive. After approved deletion, `plan RUN_ID PREVIOUS_ARCHIVE` must reproduce the saved plan hash before seeding. `seed` checks existing progress and refuses unsafe replay; an uncertain write needs manual inspection. `test-start` verifies the **initial** seeded state and must precede playbook writes. The public lazygit repository receives no writes. `archive` requires the handoff and `report.md`; use `archive-run.sh OWNER/REPO CLONE OUT_DIR ARCHIVE_NAME RUN_ID` directly only for a clearly marked partial capture. The archive captures Git refs, API observations, program history, playbooks, **only the selected run's records** and shared evaluation source, plus the seed's install and every recorded agent install that still exists. `/tmp` does not survive a reboot, so archive before one; an agent install that has gone is listed as missing in the archive manifest and must be named in the report. It it compares live revisions and refs before/after and writes a checksum. Verify it before requesting deletion. `delete` rechecks live state against that exact archive and needs explicit approval of the repository. Do not repeat a prior run's receipts.

An archive is an immutable record, not a live service. After verifying it, add the run's status, report and archive to the local run index. To let others rerun it, its fixture and answer guide can then be copied into this kit as `seed/RUN_ID.json` and `seed/RUN_ID.gold.json`; **do not edit this plan to point at a new result**. If the report or method changes after deletion, keep the archive unchanged and publish a separately checksummed correction of the single report. Historical preparation documents and run artifacts stay within their run directories, so a new session can start here without reading old methodologies.
