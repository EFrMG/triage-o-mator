# Playbook evaluation plan

**This is the current plan for the next run.** Start here. It is written for the evaluator: agents under test never receive this file or any path into this kit. Run records are local and not part of this shared kit: fixture designs, old protocols and results live under `DOCS/triage-playbook-evals/seed/runs/`, verified captures under `DOCS/triage-playbook-evals/archives/`. Paths below that start with `seed/runs/` or `archives/` are inside that records directory. For the latest result, open the **highest-numbered completed run's report** from the local run index, `seed/runs/README.md`. Past outcomes are evidence for this plan, not results to copy into a new run.

## What the evaluation is for

Assess whether triage-o-mator's **playbooks help an agent make and communicate sound decisions** while its scripts preserve evidence and enforce write boundaries. A synthetic PR about some example, tests whether a reviewer spots a contradiction between a PR claim and its diff. It is not a test of lazygit features. Product behavior requires its own build or runtime test and must be reported separately.

Use evaluation findings to prioritize triage-o-mator's development. Keep test infrastructure proportionate: prefer realistic user workflows and small method corrections, and do not let pursuit of a perfect test suite displace crucial features or fixes in the main tool. Record remaining limitations honestly so they can inform those priorities.

Keep four kinds of work distinct:

1. **Judgment cases:** small, pinned issue/PR selections with positive, negative and unresolved examples. Two independent agents see the same immutable evidence and receive an explicit task for each playbook being assessed.
2. **Coverage passes:** bounded batches that test selection, screening, checkpointing and briefing at scale. A 150-item checkpoint does not mean 150 judgments were adjudicated.
3. **Script safety cases:** exact previews, stale evidence, approval and fault injection. A unit test, dry run and live private write are different observations.
4. **Real public cases:** historical frozen lazygit evidence for editorial complexity. It is read only and cannot establish today's backlog state without a separately budgeted live read.

The expected-answer guide describes checkable fixture facts and acceptable uncertainty. It does not prove a synthetic product bug reproduces or that one agent's recommendation is automatically right.

Use private synthetic items for checkable relationships and write safety, and frozen real public items for long-lived discussions, multiple authors, conflicting evidence and editorial judgment. A private fixture written by one account over a short period cannot supply authentic maintainer feedback or age. Assign private and public work to different agents in separate installs. Keep their denominators separate and never present a synthetic report as an upstream lazygit finding. The evaluator's guide and report state the fixture's origin; agents receive ordinary task text in their own installs.

Use **two lanes**. A natural workflow lane starts with a maintainer-style request, such as triaging the next 25 untriaged issues, reviewing one named PR, or preparing a brief for recently updated items. The agent follows the installed playbook, chooses the bounded selection with the normal scripts, acquires permitted evidence and hands work to a person as it would in real use. A diagnostic lane gives one named playbook a small fixed case set with known positive, negative and unresolved controls. The natural lane tests selection, sequencing and handoffs; the diagnostic lane isolates why a specific judgment succeeds or fails. Keep their denominators and conclusions separate. Do not turn every natural task into a list of seeded targets or tell the agent which contradiction to find. For example, give an agent a frozen install and ask for a 25-issue first pass and one maintainer brief, without naming the hidden control issues. Audit what it selected, what it skipped, how it used evidence and whether the brief helps a person decide. Run an independent copy of the same request if consistency matters.

A realistic request can be: _Triage the next 25 untriaged issues in this pinned repository, propose labels where the catalog fits, mark only concrete maintainer decisions for Pending review, and write one brief. Do not publish comments or change item state._ Let the agent use the normal selection and evidence scripts, choose whether duplicate or scoring work is needed, and leave a handoff another agent or maintainer could continue. A separate realistic PR request can ask for review of a named PR and a keep-open/close/defer recommendation using its diff, base context and discussion. Neither request should force every playbook to run; measure the playbooks the agent actually used and record those it did not use.

## Coverage and data expansion

Aim for **observed coverage of every contrast in the planned matrix**, using a broader set of defensible cases. Coverage means the intended behavior was exercised and its evidence and outcome retained, including an agent mistake or justified defer; it does not mean the answer was correct. A task that never reaches its intended branch leaves that branch untested. Report judgment quality separately. Complete coverage is a goal for the declared run scope, not a claim about every possible behavior or a gate on main-tool development.

Before designing the fixture, reconcile the latest completed report, its recorded corrections and the published discussion update with the matrix below. In the run's case manifest, give each contrast an identifier, planned case count, private/public source, phase, prerequisites, required evidence and observable output. Map each task to those contrasts. Record any deliberate deferral with its reason; do not remove a missing contrast merely to call the run complete. This is a planning table in the existing manifest, not a new framework or agent-facing checklist.

Use these starting sampling targets, adjusting them explicitly in the manifest when preparation or runtime cost warrants it:

- For ordinary judgment contrasts, select **three distinct cases per contrast**, with two independent attempts on the same cases. Count duplicate pairs, group packets and brief input sets as cases, rather than their individual members. Two attempts on one case are repeated observations, not two different examples. Cases may support more than one playbook when each receives its own task and attributable output.
- For costly controlled transitions, such as acquisition resume, changed head, human correction or edited brief source, plan at least **one complete before/after sequence per distinct control**. Keep content, metadata and head changes separate. Expand a control when the first sequence exposes ambiguity or materially different behavior.
- For live private operations, plan **three justified examples each of standalone comment, close, reopen and labeling**, with varied starting states. Count explanatory comments within close/reopen separately from standalone comments. Include label removal or replacement as well as additions, preserving unrelated labels. Explicitly allocate staged approval and repository-policy execution cases; policy authorization and exact approval remain governed by the write rules below. Fault injection stays in fake-GitHub tests.
- For natural workflows, retain a 25-issue triage pass, screen the complete planned private backlog in bounded issue and PR batches, and exercise public batch-and-track continuation across at least two ordinary batches, including PR evidence. Freeze batch sizes and budgets before launch. Audit every selected member for screening and every saved recommendation for support; do not equate screening counts with independently adjudicated judgments.

Expand **case diversity and adjudicated selections alongside backlog size**, rather than increasing item totals alone. The next expansion targets **180 private issues and 45 PRs**, up from 120/30, with six 30-issue and three 15-PR screening batches. Use supported run-specific supplemental issues and PRs to supply additional realistic contexts and controls, retaining selected past-failure cases and fresh held-out examples. Supplement them with frozen public examples for real discussion and review complexity. Do not silently refresh the public source or borrow evidence across snapshots.

Include **multi-file PRs** alongside focused one-file controls. Plan at least three distinct multi-file review cases: a consistent implementation/caller/test change, a cross-file behavioral contradiction, and a documentation or configuration claim contradicted by another changed file or the pinned base. Let the withheld guide allow defensible uncertainty; a changed test is evidence to inspect, not proof that the implementation works. Review and PR briefing tasks must expose the complete changed-file list, operative diffs and relevant pinned base context, and adjudication must check whether the agent connected the relevant files rather than reading one convenient patch. A deliberately partial multi-file snapshot is a separate evidence-gap control. Prefer small coherent patches over large diffs added solely for volume.

The private seed supports supplemental items, issue/PR follow-up comments and run-specific lists of file edits while preserving existing fixtures. It previews/hashes every edit, creates each PR's edits in one commit, and audits the exact changed-file set and base/result contents. Map proposed cases onto these supported fields and existing public evidence; verify preparation with disposable/fake-GitHub checks before seeding. Identify any remaining prerequisite that needs additional private preparation, its exact operation and its phase. Do not fabricate authentic maintainer reviews, passing CI or a justified PR close from metadata. If the available evidence cannot support a contrast, choose a concrete preparation change or record a justified sampling exception/defer explicitly.

Organize execution into three phases: prepare and audit the fixture and equivalent diagnostic prerequisites; run and seal the independent comparisons against immutable evidence; then run separately identified controlled transitions and serial authorized private writes. A controlled agent continuation uses a fresh task and newly pinned packet, retaining its before/after lineage. Give both attempts equivalent starting state; never let the second observe the first's live mutation as though it were an independent trial. Where the live phase is evaluator-only, report that boundary rather than claiming agent playbook coverage. Reuse the existing seed, manifest, owning scripts and retirement command; add infrastructure only for a concrete unmet requirement.

## Before a new run

Choose a new short run ID and create a **run-specific fixture file** at `seed/RUN_ID.json` **in the local records** before running the seed. It stays out of this kit until the run is over. `seed/fixtures.json` provides the pinned base topics and repository; the per-run file supplies expanded cases using the schema described in [seed mechanics](seed/README.md). Add an explicit `public_read_scope` (repository, corpus ID, inventory snapshot, source commit and fixed-snapshot offline mode for pinned diagnostics) and `briefing_batches` with positive issue/PR batch sizes that cover the planned counts. Save the withheld answer guide at `seed/runs/RUN_ID/gold.json`. The seed and evaluator freeze refuse an unknown run ID or missing scope/guide, so a future run cannot silently inherit an older fixture shape, public corpus, batch plan or answer guide. Review remote-visible titles, bodies, comments, paths and diffs for leaked answer roles. Keep the public source checkout pinned and clean. Commit or revert tracked program changes before `test-start`; local untracked run records may remain.

After seeding, audit the **initial** private state before agent work: repository identity/privacy, exact item titles and bodies, follow-up comments, exact PR file sets, diffs and heads, Actions/Dependabot state, label catalog, staged action policy, a fresh ledger and absence of old/bot backlog. If any differs from the approved preview, stop. Do not treat the seed audit as a playbook verdict. Acquire any bounded private diagnostic snapshots read-only in the seed install before `test-start`, then let `test-start` bind the cache and install digest. The seed install has no triage decisions or policy changes at this point. Agent installs copy these immutable snapshots; the evaluator does not need to patch their caches after installation.

Write a case manifest under `seed/runs/RUN_ID/` before any agent pass. It must name the repository, program/playbook hashes, source inventory or corpus, budget, intended playbook and planned positive/negative/unresolved controls. For a **diagnostic** task, freeze exact selected keys, immutable snapshot IDs, source revisions, required components and direct comparison pairs before assignment. For a **natural workflow** task, freeze the starting inventory, selection rule and budget; the agent's selected keys and snapshots are outputs to record and adjudicate afterward. If an acquisition has not yet produced a snapshot, record that as an acquisition task and freeze its resulting ID before asking for a diagnostic judgment. For PR claims about existing behavior or documentation, make the operative diff **and the pinned base file or surrounding code** available. Add discussion, reviews and checks when the recommendation needs them. A missing component stays a gap; do not silently borrow it from a different snapshot.

Natural briefing trials use the ordinary batch-and-track workflow described in `prompts/maintainer-brief.md`: create a bounded batch, screen its members, save the brief, then use `bin/batch --mark-briefed` and `--unbriefed` for continuation. For a cached offline scenario, use `bin/batch N --include-triaged --unbriefed --order updated --cache-mode offline`, adding `--kind` and `--diff` as the task requires. The copied inventory and cache provide the starting state; selected items and embedded snapshot references are outputs to audit. Do not impose an additional corpus-membership restriction or pass a corpus ID to `--snapshot` merely because a corpus supplied the cached evidence. Exact corpus-member pins belong in diagnostics or an explicitly requested corpus-analysis scenario.

For a fixed diagnostic task, select the evidence once and reuse that selection when writing both the task text and manifest packet. Distinguish snapshots selected by the named corpus from separately acquired item snapshots; a richer snapshot is not automatically a corpus member. Natural tasks specify their starting source, selection rule and acquisition budget; the agent’s selected items and snapshots are outputs. If correcting an unlaunched task’s references, retain the earlier task/manifest version and record the correction.

Before seeing agent outputs, write the case-level acceptance criteria and allowed uncertainty in a withheld guide. Name what would count as an unsupported public comment, false duplicate, false ready or false close call, and what evidence could justify `none`, distinct or defer. Include a few cases drawn from real past failures and rotate held-out cases so the run does not become a test of memorized fixture patterns. Recheck the task wording against the grading rule; an agent should not be penalized for following the stated task.

Give every agent one lane-specific install with `run-eval.sh agent-install RUN_ID AGENT private|public`. It builds `/tmp/triage-eval-RUN_ID/AGENT/` (or under `TRIAGE_EVAL_AGENT_ROOT`) with only a `private/` clone of the audited seed install or only a `public/` clone of the pinned lazygit checkout. Both kinds of clone stay at their pinned commits, so base files are readable for PR review. A public install's ledger is rebuilt as inventory only: earlier agents' decisions, scores, assessments, batches, briefs and reports are not copied. Its evidence cache is copied whole, so snapshots acquired outside the frozen corpus are still present; diagnostic tasks name exact snapshot IDs for that reason. The command refuses to run if the seeded install, either source checkout or any playbook changed since `test-start`, and records each agent's lane, paths, heads and install digest in `seed/runs/RUN_ID/agent-installs.json`. Start each agent in its own `private/triage-o-mator/` or `public/triage-o-mator/` install, and keep the seed's install at `/workspace/lazygit-clone` untouched until all blind outputs are sealed; it is the base for later private agents and the serial write phase. **This whole kit is evaluator-only.** `test-start` writes `freeze.json` for the evaluator; agents receive no evaluator handoff. Give each agent its concrete launch context and frozen task text, never this plan, the run directory, `seed-state.json` (its keys carry case roles), the fixture preview, seed source, audit, expected answers, prior reports or another agent's notes. An install's program links still resolve to this checkout, so the kit stays reachable on disk; the boundary is the instruction to work in the assigned install plus the agent's command log, and the report must say so rather than claim enforced isolation. Fix the model and reasoning settings in the manifest. If a selected snapshot or case list changes, create a new version of the case manifest and mark the earlier pass separately.

Hold the fixture and program still during a blind comparison. Finish the initial audit and snapshot selection, then make **no GitHub or source edits affecting selected items, no policy changes and no program/playbook commit changes** until both agent outputs are sealed. Run private write-safety cases afterward on separately identified items or in a new phase with fresh revisions. Recheck repository identity, source HEAD and playbook hashes at the end. If a source or program revision changes, stop the affected comparison and record a new packet; do not quietly combine before/after observations. An earlier run allowed evaluator-side writes during ongoing briefing and saw an unrelated program HEAD change, which made this boundary harder to explain.

Separate fixture preparation from blind adjudication where possible. A preparer may inspect the seed and guide to verify the fixture; the blind evaluator should not read that material until both agents' first outputs are saved. If one person must perform both roles, record the prior exposure and avoid claiming evaluator blindness. The local run index links earlier reports where this distinction mattered.

## Assign agents and bounded playbook tasks

Launch two fresh, isolated agents for each bounded task: one for independent attempt `a` and one for `b`. Do not reuse either agent for the next task. A coherent natural request may call on several playbooks within one bounded task, but a large briefing is split into its planned batches, each with a new pair. A diagnostic task names one playbook and one fixed packet. Use distinct private and public agent rosters and never assign both repositories to one agent. Record unique agent IDs such as `p01a`/`p01b` and `u01a`/`u01b` in the manifest, with the model, reasoning effort, task and lane. Start agents without inherited conversation (`fork_turns=none`). This keeps a long run from accumulating hundreds of thousands of context tokens in one agent. For an independent diagnostic comparison, give both fresh agents the same frozen prerequisite packet. For a workflow continuation, copy only attempt `a`'s sealed local artifacts into the next `a` install and only attempt `b`'s into the next `b` install; record source paths and digests, then compare the resulting workflows separately. Never pass one attempt's answer to the other or silently mix their local state. Keep live GitHub writes with one serial evaluator after the blind reads.

Separate **launch context** from **task text**. `agent-install` validates the selected repository and the install's `AGENTS.md` link, then prints and records a `launch` object with the concrete absolute `working_directory`, `instructions_file` and a short routing `message`. Set the spawn API's working directory to that exact path when supported. If the API cannot set it, supply the recorded launch message before the frozen task text; it explicitly names the working directory for every shell command and the `AGENTS.md` to read first. Do not ask an agent to resolve `AGENT_ID`, infer a path from its task name, inspect the evaluator's install index or discover other installs. The two attempts receive different routing paths but byte-identical task text and equivalent evidence. Save the launch context separately from the task digest, and record the actual startup directory and first successful command directory. If the runtime starts in the program checkout, say so; explicit routing does not establish enforced isolation.

Capture chronological command/tool-call logs from the evaluator's runtime transcript. Verify that transcript capture is available before launching a blind task. Agents should do ordinary triage work and report their evidence and outcomes; do not require custom logging scripts, shell wrappers or command re-escaping. Seal the raw transcript, output and artifact digests when each attempt finishes. Extract command logs from that retained transcript without rewriting it, and report any missing trace or commands outside the assigned scope.

After an agent has stopped and its output is sealed, run `run-eval.sh agent-retire RUN_ID AGENT` before creating more installs. Never retire a checkout while an agent is running or may resume work in it. The command verifies the completed seal, retained artifact hashes, registered paths, pinned HEAD and absence of checkout changes, then removes only the disposable parent source files and Git directory. It retains the complete `triage-o-mator/` install at its registered path for same-attempt artifact transfers and final archiving. Cleanup is recorded in `seed/runs/RUN_ID/agents/AGENT/retirement.json`; an interrupted cleanup can resume using the same command after its retained install is revalidated. A retired checkout cannot supply source context for later work: create a fresh agent install for each new task. Keep the seed and public source checkouts, and every retained agent install, until the archive is verified. This keeps redundant parent checkouts from filling `/tmp`.

Two independent attempts reveal disagreements; they do not estimate a reliable accuracy rate. If a future report needs a rate or before/after comparison, repeat the same frozen tasks across additional trials with the model, budget and environment held fixed, and keep the per-trial traces. Do not turn two matching answers into a confidence score.

Every agent works in its own install and receives a separately written task, saved under the run directory before it is sent, plus the concrete launch context described above. A diagnostic task names the frozen corpus or exact snapshot scope it needs, on either repository track. A natural public task names the repository, starting cached inventory, selection rule and read budget; its normal batch selects the evidence. Ordinary repository context comes from that install's `AGENTS.md`, `config/repo` and scripts. The `briefing_batches` sizes recorded in evaluator-only `freeze.json` are the planned denominator for Maintainer brief coverage; give a fresh agent pair one bounded batch at a time and retain the selected, screened and remaining keys across batch records.

Do not ask an agent to apply several playbooks wherever they seem relevant in a **diagnostic** task. Each such task should specify: the named installed playbook; exact keys and snapshot IDs; required evidence categories without revealing the intended finding; the owning script record or brief to save; the request/time bound; allowed side effects; and what to report when the answer is `none`, distinct, deferred or unassessed. For an independent comparison, give both agents **the same packet and task text** in isolated installs, then seal both outputs before either sees an answer guide or the other's notes. Save the actual task text and a command/tool-call log under the run directory; record failures and retries as well as successful outputs.

Check diagnostic prerequisites against the actual install contract. For labeling, judge fit against the saved catalog: a process proposal can reasonably fit a broad `enhancement` label. Choose a no-fit control only when its exclusion is defensible under that catalog; otherwise report that contrast as untested. For automated-action proposal preparation, supply source-bound saved writing actions through the owning scripts in each fresh agent install, and record those equivalent local prerequisites in the packet before launch. Keep the audited seed untouched. Test blank or non-writing actions separately: the agent should record an explained `skipped` assessment, without inventing a writing action or proposal. A completed skipped record is coverage of that selected item, not eligibility or approval to publish.

Use this task form, filled with real paths and IDs:

> Follow `prompts/PLAYBOOK_NAME.md` for these exact `KIND:NUMBER` keys and immutable snapshots. Read the listed body, complete discussion, operative PR diff and pinned base context; inspect the strongest fact against your likely call. Stay within `N` acquisition requests. Save the playbook's owning record or brief for **every** selected key, including no-finding or deferred outcomes. Report selected and remaining keys, revisions, gaps, requests, elapsed time, record IDs and any correction. No GitHub write is authorized by this task.

Do not force a positive result just to fill a matrix cell. If the fixture has no defensible PR close, record zero positive closes and leave that branch untested. A later task to edit a brief, change a head or inject an uncertain response must be separate from the sealed blind comparison. For natural workflow tasks, record the person's original request, what the agent selected, what it left behind and the final artifact a maintainer would actually read; grade the end state and tool path, not only a final sentence.

## Planned case matrix

Select an inspectable denominator for each row and freeze it in the case manifest. These are **requirements for a future run**, not claims about any past run.

| Playbook or flow      | Minimum decision contrast                                                                                                       | Required output and main risk                                                                                                                                                                 |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Prepare analysis      | Complete, partial and interrupted/resumed acquisition.                                                                          | Corpus/job status and fixed snapshots; finished progress must not imply coverage or freshness, and offline reads make zero requests.                                                          |
| Auto triage           | Useful unanswered question, already-answered or repeated question, and a true `none`/defer.                                     | Source-bound decision for every key; count unjustified public comment suggestions separately.                                                                                                 |
| Label items           | Clear match, no fit, stale catalog and human correction.                                                                        | Local proposals/no-fit records plus exact item-label preview and bounded outcomes; preserve unrelated labels.                                                                                 |
| Score items           | Same pinned issues/PRs scored blind twice, an evidence gap, and distinct content/metadata/head freshness changes.               | Dimension reasons and marks, current/unassessed status and stale refusal; agreement is not correctness.                                                                                       |
| Find duplicates       | Same cause with different words, same title with different cause, unresolved discriminator and recorded not-duplicate.          | Both-sided direct signals and saved verdicts; no safe survivor inferred from title or shared defect alone.                                                                                    |
| Review PR             | Wrong diff, unsupported doc edit, compatibility boundary, partial diff, safe no-finding, and substantive review/check feedback. | Head-bound review assessment with operative diff **and base context**, contrary facts, reviews/checks or named gaps.                                                                          |
| Recommend PR closures | Justified close, keep-open and defer, with changed head/activity control.                                                       | Exact explanation and pinned state; an absent positive fixture is explicitly untested.                                                                                                        |
| Organize groups       | Relevant mixed issue/PR set, no-group control and edited-scope case.                                                            | Frozen candidate origin, member relevance and one clear maintainer question.                                                                                                                  |
| Automated actions     | Stage, question/answer edit, rejection, stale preview, direct execute, blank-action skip and uncertain transport.               | Exact proposal, policy, preview, receipt and before/after state. Use fake GitHub for fault injection; live private writes are serial, each approved exactly or covered by an approved policy. |
| Maintainer brief      | Distinct issue/PR batches, relevant base contradictions, and ordinary public batch-and-track continuation.                      | Screen every selected member, checkpoint only screened batches, and expose important omissions and counterarguments.                                                                          |
| Polish briefs         | Four saved briefs, a conflict between calls, and an edited source after planning.                                               | One readable master bound to exact input digests; audit what useful nuance disappeared.                                                                                                       |
| Item brief            | One issue and one PR with a material contrary fact or gap.                                                                      | Decision, evidence link, strongest hesitation and next check; no implied write approval.                                                                                                      |
| Review appeal         | Closed PR with original and competing claim, later discussion and incomplete-source control.                                    | Pinned watch/action reads that separate claims, observed closure, appeal and approval; no automatic reopen.                                                                                   |

TUI integration and PTY tests are outside playbook evaluation runs. Assess terminal navigation, drafts, scrolling, stale replies and interactive usability in a separately scoped UI validation effort. Existing project test results may be cited separately, but do not treat them as playbook observations or add PTY smoke work to the run.

## Adjudicate and write one report

Score **selection coverage, evidence fidelity, judgment, handoff clarity and side-effect safety separately** for every tested case. Count selected, completed, skipped, deferred and untested keys. Report false positive comments and closes apart from missed useful work. A completed record proves the scope was handled; it does not validate the recommendation. Compare the two blind answers first, then inspect the withheld guide and full source. Record source corrections, especially a wrong snapshot pin or a missing base document, without rewriting the original blind answer.

Assign coverage from the manifest's contrast-level observations, retaining planned and actual case counts for each independent attempt. **Observed** means every declared required contrast was exercised with inspectable evidence and outputs; **mostly observed** means the main workflow was exercised but secondary controls are missing; **partly observed** means a substantial branch or workflow is missing; **not tested** means no qualifying observation. Name missing contrasts even for mostly observed playbooks. Keep agent, evaluator-only, live, offline and fake-transport observations distinguishable; a fake fault test cannot fill a live or agent-observation gap. An incorrect recommendation can still be observed coverage and must remain a judgment failure in the results.

Save **one** `seed/runs/RUN_ID/report.md`. It is both the shareable discussion update and the technical result. Open with plain-language answers to: what was tested, what happened, what worked or failed, and what remains unknown. Then include a per-playbook status table (`observed`, `mostly observed`, `partly observed`, `not tested`) with denominators, a disagreement/correction section, exact side effects and evidence links. Keep full keys, revisions, hashes, request counts, task text, receipts and raw observations in linked run records rather than crowding the opening. Never call seeded, planned, dry-run or unit-test cases live playbook results. Do not make a second `discussion_*.md` or `summary.md` for a new run.

The report must distinguish synthetic private cases from public real cases, a source-based PR finding from runtime reproduction, and a saved local suggestion from a GitHub write. State whether the report was posted anywhere; writing the file alone is not publication. Preserve the previous run's report and ratings as historical evidence, not a denominator for the new run.

Keep local triage decisions, explicit Pending review requests and GitHub write approval as separate states. A group, score or brief can support a human decision without flagging Pending review or authorizing an action. A live private write is authorized in one of two ways. A **staged** proposal or a directly composed comment, closure or reopening needs a person's approval of that exact target, operation and text. A write made under **repository policy**, an action type set to `execute` or the bounded label pass, needs a person's approval of that policy change once, naming the action type and the private repository; the writes it covers then run without further approval and are checked from their receipts. Record which of the two authorized each write, and restore any policy changed for a test before archiving. For each live private write, retain the exact target, operation, public text, policy, preview/approval hash, live recheck and receipt; closure or reopening posts its explanation first. No public repository write is permitted.

## Reproducible run and archive sequence

`README.md` is the short entry point; this plan is the single current method. `seed/README.md` explains fixture mechanics. `run-eval.sh` and `archive-run.sh` are the owning run tools. Check the current private remote before planning. An old local clone may remain, so pass a verified previous archive for that same private repository when the seed requires it; an archive of the old `lazygit-test` repository is not a previous archive for `lazygit-clone`.

```sh
KIT=/workspace/triage-o-mator/tests-playbooks
RECORDS=/workspace/triage-o-mator/DOCS/triage-playbook-evals # local; override with TRIAGE_EVAL_RECORDS
: "${RUN_ID:?Set an unused run ID after reviewing seed/RUN_ID.json}"
archive_args=()
if [[ -n ${PREVIOUS:-} ]]; then
  $KIT/run-eval.sh verify "$PREVIOUS"
  archive_args=("$PREVIOUS")
fi
$KIT/run-eval.sh plan "$RUN_ID" "${archive_args[@]}" # read-only preview; save and review its hash
$KIT/run-eval.sh seed "$RUN_ID" PLAN_SHA256 "${archive_args[@]}" # private GitHub writes only after exact seed approval
$KIT/run-eval.sh test-start "$RUN_ID" # audit before agent work; writes freeze.json
$KIT/run-eval.sh agent-install "$RUN_ID" p01a private # repeat with fresh IDs for each private task pair
$KIT/run-eval.sh agent-install "$RUN_ID" p01b private
$KIT/run-eval.sh agent-install "$RUN_ID" u01a public # separate agents for real public evidence
$KIT/run-eval.sh agent-install "$RUN_ID" u01b public
# Freeze case manifest and exact agent tasks; run bounded passes.
# After each agent stops and its output is sealed:
$KIT/run-eval.sh agent-retire "$RUN_ID" p01a # repeat for each finished agent
# Keep retained installs; write report.md, then archive and verify.
$KIT/run-eval.sh archive "$RUN_ID" ARCHIVE_NAME
$KIT/run-eval.sh verify "$RECORDS/archives/ARCHIVE_NAME.tar.gz"
# After separate approval of the exact repository deletion:
$KIT/run-eval.sh delete "$RECORDS/archives/ARCHIVE_NAME.tar.gz" --confirm-repo OWNER/REPO
```

Set `PREVIOUS` to the matching verified archive when an old local clone exists; leave it unset only for a genuinely fresh target with no old clone or remote. If the previous remote still exists, `plan-after-reset RUN_ID PREVIOUS_ARCHIVE` makes a read-only prospective preview only after verifying it still matches the archive.
